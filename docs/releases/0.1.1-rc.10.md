# 0.1.1-rc.10 development candidate

RC10 combines **reduced CPU frame copies** with **experimental 8K support**.
It is not yet installed or released. The combined binary still needs a clean
required codec matrix, session churn, 8K pixel checks and browser measurements.

| Feature | Behavior |
| --- | --- |
| Matching H.264 / HEVC layouts | Iris writes directly into surface storage |
| Other supported linear layouts | GPU transfer to stable surface storage |
| AV1 hidden references | Independent retained surfaces; GPU publication |
| VP9 GPU build | Kernel CAPTURE buffers exported internally to the GPU |
| Unsupported GPU layouts / CPU images | CPU fallback / explicit readback |
| Experimental 8K | Shared side, frame-area and memory checks |

A GPU transfer avoids CPU pixel publication but still moves pixels. It preserves
NV12/P010 bytes, caller guards and padding. Completed source buffers stay pinned
until all visible/hidden owners are published and GPU completion is confirmed.
An uncertain GPU fence stops decode without a CPU retry after destination writes.
Direct AV1 CAPTURE remains disabled to preserve hidden-reference ownership.

Teardown waits for STOP's final marker. Direct mode uses separate scratch
storage so that marker cannot overwrite the published frame. Both input and
output ports are then stopped before either allocation pool is released.
Unexpected empty error buffers fail pending owners without drain/rebuild loops.

## 8K limits

Normal builds keep the 4096-pixel maximum side. `experimental-8k` permits sides
up to 8192 and a rounded frame area of `(8192/16) * (4352/16)` macroblocks.
8192x4352 and its portrait orientation fit; 8192x8192 does not.

Per-frame storage is limited to 128 MiB. CAPTURE and standalone surface storage
each have a separate 1 GiB budget. Kernel-allocated CAPTURE is checked before
allocation/growth too. These budgets do not include all firmware or process
memory. Padded 7680x4320 storage is 49,766,400 bytes for NV12 and 99,532,800 for
P010. AV1 remains 8-bit/no-film-grain; P010 coverage concerns HEVC Main10.

## Evidence and remaining checks

Earlier GPU tests matched 48 NV12/P010 transfers through 4K, including padding
and caller guards. A captured 32-frame 4K AV1 replay matched software pixels
and frame order with zero CPU publication-copy bytes. Ordinary FFmpeg AV1
input failed during assembly before GPU publication; complete captured VA
buffers are required by the successful replay path.

An earlier 8K candidate matched all seven coded AV1 frames and showed Chrome
playback at 5 fps. Its approximately 30 fps test failed: CPU publication alone
measured 43.3 ms against a 33.3 ms frame budget. Those results motivated this
GPU integration; they do not qualify the current binary or sustained 8K speed.

Previous combined candidates passed H.264 1/30/full, GL/export, resolution
changes, long playback and HEVC/Main10, then failed VP9 session reuse. The
latest kernel-buffer diagnostic matched its first requested VP9 output with
14 GPU publications, but the following session stalled and added two Iris
system errors. Earlier memory-accounting BUGs and a separate FPAC Oops have
unproven causes. The new close ordering is host-tested, not hardware-qualified.
No failed run has been relabeled as a pass or retried automatically.

## Build and package

```sh
V4L2_VA_BUILD_FEATURES='system-av1 gpu-copy experimental-8k' \
  ./tools/build-rust-driver.sh /tmp/qcom-vaapi-rc10
```

The vendor label identifies RC10, GPU frame transfers and experimental 8K.
The AV1 companion remains unchanged. GPU packages include EGL/GLES/GBM runtime
dependencies. Packaging installs userspace only; kernel patches and the power
helper are not activated. Use the README's package command with the corresponding
FFmpeg source licenses.

Sustained 8K30/60, Firefox 8K, 8K VP9/HEVC and broad suspend/resume reliability
remain unqualified. RC10 publication and system installation await the required
checks on the exact combined binary.
