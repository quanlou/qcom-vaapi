# 0.1.1-rc.9 development snapshot

A live RC8 Chrome profile found a decoded-frame snapshot in `capture_copy`
followed by a second copy into caller storage. RC9 allows the completed CAPTURE
slot to remain pinned until its pixels are copied into an imported VA surface,
omitting the intermediate snapshot for ordinary display publication. A CPU
image request later normalizes the retained imported planes on demand. Hidden
aliases that require independent retention still use a snapshot.

RC9 also permits direct decode into an imported buffer when its pitches,
offsets and size match Iris's full padded storage layout. Every declared target
must be compatible before a context selects direct capture. The existing
negotiated-layout checks remain in place, and imported direct targets complete
during EndPicture because Iris does not publish a dma-resv completion fence.
Incompatible imports use the single-copy publication path. Full-width copying
uses two plane transfers instead of one memcpy call per row.

These changes do not replace the Iris kernel module or activate the optional
power service. Earlier kernel reopen/corruption failures remain unresolved.
Removing the intermediate copy is not a claim of zero-copy for incompatible
layouts: the remaining transfer needs a GPU path or compatible browser storage
to disappear. CPU image requests necessarily copy pixels.

Host validation covers NV12/P010 pixel parity, caller prefixes/gaps/padding/tail
preservation, direct-layout rejection, retained fd identity, snapshot-free
publication, and CPU image correctness after the working CAPTURE buffer is
reused. Live Chrome CPU improvement and imported direct decoding remain pending
hardware measurement; no new Chrome/Firefox 4K60 qualification is claimed.

Checks: 294 Rust tests passed (4 fixture-dependent tests ignored), strict
all-target/all-feature Clippy and formatting passed, and the system-AV1 release
build completed. Four host stress cases and the concurrent suite passed. A
30-second isolated browser smoke test recorded 1,805 direct completions and
closed cleanly with no checked kernel fault afterward. That fixture used
driver-owned allocations, so it does not qualify the new imported-buffer path
or prove a CPU reduction for the user's YouTube session. Its playback counters
also do not establish sustained 4K60 presentation.
